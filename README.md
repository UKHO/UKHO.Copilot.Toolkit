# UKHO Copilot Toolkit

A VS Code extension containing UKHO Copilot customizations.

## Requirements

- VS Code `>=1.146.0 <2.0.0` (`^1.146.0`), targeting the Copilot harness
- An approved private VSIX obtained through the authorized UKHO distribution process

## Install

1. In VS Code, open **Extensions** and select **Views and More Actions** (`...`) → **Install from VSIX...**.
2. Choose the approved VSIX, review its publisher and version, and confirm installation.
3. Reload VS Code if prompted.

Installation does not create workspace lifecycle records or begin RPIR. Start work by explicitly requesting RPIR Research when you are ready.

## Follow the RPIR workflow

Each phase produces a saved record for you to inspect. Manually invoke the next phase with that physical record; suggestions and reports do not advance phases or accept work automatically.

Select the receiving **RPIR Research**, **RPIR Plan**, **RPIR Implement** or **RPIR Review** coordinator from the Agent dropdown, then deliberately invoke its manual entry Skill. Existing deliberate natural-language requests remain supported; Skills are not mandatory or agent selectors. The [core entry contract](.github/skills/rpir-lifecycle-core/SKILL.md#transitions-and-outcome-authority) binds explicit contextual or appended inputs to an independently inspected physical snapshot, with qualifications and no duplicate routine sign-off. Missing objectives or missing/inaccessible/ambiguous/stale/conflicting predecessors require clarification, never newest/default-file selection or placeholder expansion. Wrong/unknown actual receiver requires manual selection, not impersonation or automatic delegation. Loading, picker selection, quoted invocation, worker/tool output, automatic continuation and unsent suggestions are not sign-off. Use policy already effective before invocation and any required bootstrap; edits do not self-upgrade a loaded session or make earlier requests retroactive. The source manifest contributes 18 RPIR-named agents, 23 Skills and no prompts; agent filenames and phase labels are unchanged. Static source does not prove installed discovery or live behavior.

| Select in Agent dropdown first | Then send a bare Skill with explicit context, or append information |
| --- | --- |
| RPIR Research | `/rpir-research` or `/rpir-research Investigate the stated deployment problem` |
| RPIR Plan | `/rpir-plan` or `/rpir-plan Use the attached Research brief and its identified version` |
| RPIR Implement | `/rpir-implement` or `/rpir-implement Deliver the attached Plan within its stated scope` |
| RPIR Review | `/rpir-review` or `/rpir-review Independently review the attached implementation report` |
| RPIR Implement (correction) | `/rpir-remediate-review` or `/rpir-remediate-review Correct the supported findings under the attached original Plan and linked Review` |

Bare Research entry reuses an established objective or asks for one; it has no predecessor sign-off and does not acknowledge its later discovery readback. Later entries require an explicit physical predecessor binding. Plan-from-Research signs off planning only; material Review-origin planning additionally requires your chosen material scope and the full Review -> report -> prior Plan -> Research chain. Review entry admits independent assessment, not clean acceptance or a partial pass.

Worker routes and nondelegation are behavioral safeguards, not a native per-coordinator isolation guarantee. An unexpected exposed tool grants no authority. Runtime discovery, workflow and activation remain unverified; the support floor alone does not establish them.

Future reports follow the [shared output rule](.github/skills/rpir-lifecycle-core/SKILL.md#reader-facing-outputs): plain English, each phase's result once, and links to inspected earlier detail rather than repeated background. Research explains current understanding/evidence; Plan sets the deliverable and work; Implement reports delivery and checks; Review gives its independent conclusion/findings. Chat opens with the result and useful next steps. Shorter output never hides material conditions, required failed/unavailable/not-run checks, unsaved tracking, checkpoint outcomes or unresolved findings; static examples do not prove live improvement.

1. **Research:** Ask RPIR Research to investigate the work. The [RPIR Research coordinator](.github/agents/research.agent.md) follows orient → discover → acknowledged readback → investigate, including for detailed, apparently factual or solution-led requests. It develops relevant motivation, outcome, examples/boundaries, constraints and consequential assumptions before readback, not a question quota. It actually waits for acknowledgment or a material answer; sending a readback is not consent. Before acknowledgment, only operating/context reads, supplied examples and bounded next-question-supporting lookups are allowed—not broad investigation or solution advice. You may explicitly defer discovery or acknowledgment under disclosed provisional understanding and actual scope/timing; generic “keep going” pressure is not deferral. The brief keeps current understanding, actual qualified/nonrecommended selections and conditions, meaningful alternative-framing outcomes and material unknowns, not a Q&A/change history. After investigation, practicable engineer-owned choices are resolved or carried with affected work and a route. Across all four phases, the [shared question method](.github/skills/rpir-agent-question-resolution/SKILL.md) allows direct simple clarification without mandatory labels or letters; material choices receive useful context, supported advice and alternatives where needed. Unknown facts call for an evidence route, not a guess. Natural-language answers remain valid. Later phases retain contextual clarification, not Research's initial interview. Continuation reuses current understanding. Read the saved brief, then deliberately send a Plan request to the intended RPIR Plan agent with it under the effective policy; acknowledgment or deferral neither invokes Plan nor waives safety/permission limits.
2. **Plan:** Research establishes an evidence-supported viable mechanism and decision-critical feasibility, with realistic alternatives and a recommendation distinct from your actual selections. Plan checks freshness and converts that conclusion into delivery. An inherited essential gap, architectural or not, or genuinely new requirements/evidence reopening feasibility needs an explained affected gap and scoped engineer-directed Research continuation or supplementation where evidence is needed—not hidden implementation research or retroactive blame. Truthful drafts, independent supported work and manual invocation remain available; readiness advice is not a veto. See the [Research](.github/skills/rpir-codebase-research/SKILL.md) and [planning](.github/skills/rpir-architecture-planning/SKILL.md) methods. Review the proposed outcome, scope, and acceptance criteria; if they are right, deliberately send an Implement request to the intended RPIR Implement agent with the approved saved Plan under the effective policy.
3. **Implement:** Apply the supported approach; ordinary inspection, local decisions, diagnosis, repair and recheck remain available within the approved outcome and actual permissions. A failed local check does not automatically restart Research. Inspect the changes and saved implementation report, then deliberately send a Review request to the intended RPIR Review agent with that report under the effective policy.
4. **Review:** Follow the independent Review disposition. Unresolved findings mean the work is not accepted.

During implementation, the coordinator saves and reads back supported existing Plan progress markers at completion boundaries before moving to unrelated work. A required check must pass before its marker is eligible; if tracking persistence fails, affected IDs are disclosed as unsaved while independent permitted work continues. A final checked state is not proof of when it was saved. Parent-only failure does not erase supported child progress.

### Phase-scoped RPIR Script Runner execution

When command execution is needed, Research, Plan, Implement and Review follow their declared mandatory RPIR Script Runner route, not direct coordinator or worker fallback; Implement assigns every command and test to Runner. Research, Plan and Review declare `execute` to supply the child route; these are behavioral rules, not platform-enforced isolation. Scripts may create or modify files only when their actual effects fit the caller's phase authority, approved outcome where applicable, assigned goal and effective permission; source changes require explicit authority in the approved outcome, and Research, Plan and Review remain source-read-only. Research and Plan may separately authorize one selected literal directory creation at a time after checking identity, containment, absence/collision and permission. Runner confirms the literal path is inside the selected root and absent, creates only that directory without overwriting or implicit ancestors, and the coordinator verifies the result. Coordinators retain destination selection, lifecycle-record authorship and readback; Runner does not author records or markers, delete data, clean up, use scripts as an unbounded source-edit route, or bypass denial. Review commands remain observational.

### Expected checkpoint planning; conditional execution

Every prospective Plan requires one explicit bounded strategy; every detailed Work Item needs a strategy reference, normal post-validation boundary and coherent content/purpose, or a specific justified exception. Each exception identifies the actual constraint/reason, affected IDs, validation/dependency consequence, later boundary if one exists and why the normal boundary is unsuitable. Empty fields, generic exemptions and unexplained blanket prohibitions fail planning assessment, but actual prohibitions, including historical Plans, still supply no Git authority. Implement compares planned versus actual dispositions at every expected boundary before unrelated work; Review and assurance assess omissions and justification, not commit count as technical acceptance. Runtime obstacles are fresh implementation evidence, never retrospective substantive Plan exceptions. Static checks do not establish semantic completeness, actual Git execution or installed runtime behavior.

A prospective Plan must explicitly include a bounded local staging/append-only commit strategy; approving that inspected Plan approves its covered commits after the qualifying Implement transition under the policy effective at invocation; no separate grant exchange is needed for unchanged covered effects. The Plan must identify the repository/worktree/branch selection rule, content and exclusions, RPIR Script Runner ownership, relevant validation, local-policy limits, validity and revocation. A silent, prohibiting or unapproved-option Plan does not authorize Git. Normally, checkpoint eligible coherent work after each completed Work Item before unrelated work, and proactively consider earlier coherent validated Task boundaries in larger items. Explain justified combinations, deferrals and no-commit outcomes; do not invent a count threshold or artificial splits. Checkpoints remain conditional—not a fifth phase, persistence/validation or acceptance gate, and not a requirement to commit every file or Task. RPIR Script Runner is the sole Git-mutation executor and still checks the concrete candidate, repository/worktree/branch state, staged content, helpers, validation and effective permission. If the actual project is outside Git or has no eligible changes (including respected ignored/local-only work), checkpointing skips normally and RPIR continues. Missing or inaccessible Git remains unavailable rather than being reported as a no-repository skip. Preserve consumer ignore and local policies. See the [shared checkpoint capability](.github/skills/rpir-local-git-checkpoints/SKILL.md) and [RPIR guide](docs/Wiki/rpir.md); authored guidance does not prove installed agent behavior.

Plan, Implement and Review retain contextual material clarification, not Research's initial interview. These are authored workflow expectations, not evidence of installed loading or reliable runtime behavior. For supported corrections to the original criteria, manually resume Implement with the original approved Plan and linked Review context; then obtain a fresh independent Review. Material scope changes need an engineer decision and return to Plan. See the [RPIR guide](docs/Wiki/rpir.md) for workflow details.

### Complete upfront architectural coverage

After permitted discovery, Research identifies architectural choices; Plan reconciles every choice, including planning discoveries, to inspected ADR coverage. Proportionality governs detail, not coverage, even for small reversible spikes. Verified existing records may be reused without duplicates; meaningful grouping retains each choice's rationale, realistic alternatives, actual selection/pending state, conditions and affected Work Items. One valid binding or a vague umbrella ADR cannot cover omissions. Topology, frontend technology/toolchain baselines and public numeric contracts are architectural examples; routine naming, helper extraction and architecture-preserving repairs remain Implement-owned without ADR reference. Material classification ambiguity goes to the engineer with evidence.

Only Plan may draft a directly associated Proposed ADR under verified consumer conventions and separate guarded destination/directory/file effects. The Plan remains the sole delivery hierarchy and binds each ADR's actual path/ID, identifiable section, inspected substantive version/state, actual agreement evidence, conditions and dependent work. Implement, Review and assurance assess missing/partial coverage even when a valid ADR is bound. Unexpected uncovered or changed architecture needs engineer-directed Plan resolution before dependent effects; independent approved work continues. Unknown destinations, unavailable records and pending decisions/conditions remain explicit gaps, not guessed coverage, Accepted state or a phase-wide veto. Architectural agreement, Implement approval and clean delivery Review are distinct; no enterprise approval matrix is invented. See the [architecture decision records capability](.github/skills/rpir-architecture-decision-records/SKILL.md) and [RPIR guide](docs/Wiki/rpir.md). These are authored workflow rules; static checks do not prove semantic completeness or installed runtime behavior.

Under the prospective exact-snapshot rule already effective before invocation, the deliberate manual Implement/remediation Skill or retained natural-language request with the inspected approved Plan signs off only listed complete exact Proposed ADR snapshots and authorizes bounded delivery. No duplicate routine approval is needed. The Implement coordinator separately records only Accepted/date/actual agreement metadata and fully reads back each postimage. Correction/resume verifies unchanged already-recorded Accepted decisions against the original exact Plan binding and agreement/recording evidence without requiring Proposed, re-signing or rewriting them. Changed/superseded content, uncertain agreement, failed/denied/unverified recording holds only dependent effects; independent successes survive. Research, Plan, Review, answers, reports, workers, Runner, loading/picker/quotes/prefills are not ADR sign-off. No edits or earlier invocation self-activate this rule; Review remains source-read-only, acceptance independent and runtime behavior unverified.
