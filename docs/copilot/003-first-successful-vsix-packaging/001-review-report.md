## Findings

### [Medium] Non-read archive members can conceal mismatched local names

- **Classification:** Actionable; original-criteria correction (Work Item 2, preserve archive-boundary guarantees).
- **Location and evidence:** `scripts/verify-vsix-boundary.cjs`, `archiveMembers`, `readArchiveMember` and `verifyArchiveContents`. The inventory checks central-directory names; local/central name equality is enforced only when a member is extracted, while `verifyArchiveContents` extracts only README, package identity, VSIX manifest and changelog. An in-memory otherwise valid ZIP with an allowed `extension/other.txt` central name but a different local-header name passed `verifyArchiveContents`; direct `readArchiveMember` on that member rejected it with `ZIP local and central member names differ for extension/other.txt`.
- **Impact and smallest supported next action:** Archive consumers can reject or interpret such a member differently even though boundary verification passes. Under the original Plan, check local/central consistency for every expected archive member and add a focused negative case; do not republish or overwrite the existing candidate to prove this fix. Revalidate the actual artifact as appropriate under the Plan.

### [Medium] Identity-looking CDATA is accepted as a VSIX Identity element

- **Classification:** Actionable; original-criteria correction (Work Item 2, reject invalid identity members).
- **Location and evidence:** `scripts/verify-vsix-boundary.cjs`, `parseVsixIdentity`. Its regex searches XML text for `<Identity` without distinguishing element nodes from CDATA. In a read-only in-memory probe, XML with matching `<Identity ...>` text *only inside CDATA* returned `{"Id":"ukho-copilot-toolkit","Publisher":"ukho","Version":"1.0.0"}` instead of rejecting the missing real identity element.
- **Impact and smallest supported next action:** The identity check can certify a manifest with no actual Identity element. Validate one genuine Identity element in the expected manifest structure, without assuming raw regex matches are XML nodes; add the CDATA negative case and rerun relevant checks without adding a consequential dependency outside Plan approval.

### [Low] Negative tests accept unrelated exceptions as intended rejection

- **Classification:** Actionable; original-criteria correction (Work Item 2's negative-case evidence).
- **Location and evidence:** `scripts/test-vsix-boundary.cjs`, the `negatives` loop uses `assert.throws(() => verify(entries, source), undefined, ...)` for every case. This asserts only that *some* exception occurs, not that the intended invalid identity, notes or README condition caused it.
- **Impact and smallest supported next action:** A fixture or ZIP extraction regression could leave the suite green without exercising the claimed rejection. Assert an appropriate diagnostic for each case and rerun the focused tests; do not treat the existing 15-case pass alone as proof of each intended failure path.
