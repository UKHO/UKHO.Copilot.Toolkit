# Implementation plan

## Outcome, boundaries, and chosen approach

**Deliver one coherent replacement of RPIR's restrictive operating model:** diagnose, repair, rerun and obtain independent review within an approved outcome. Remove conflicting rules rather than add another exception layer. A partial report is a checkpoint, not the deliverable.

- **Bounded deliverable:** reconciled repository policy, contributed agents/prompts/skills/templates, recovery-contract tests, checks-only CI and existing explanatory documentation. Success means the authored contract supports ordinary recovery, preserves material decisions and real permission boundaries, passes its static regression suite, and receives independent review. Actual installed-agent effectiveness remains a separate, explicitly unvalidated outcome while runtime activation is held.
- **Included change boundary:** the existing policy owners and dependent validation/documentation files enumerated once in the register below. Preserve artifact identities, discovery roots, package contributions, public package identity/version and unrelated content. This is one delivery effort, not separate approval cycles for each file or wording defect.
- **Excluded:** source/application features under `src/`, dependencies or lockfile changes, manifest synchronization, new customization identities, historical-record rewriting/migration, release metadata, commits, publishing, installation, runtime activation, VSIX creation/overwrite, remote mutations, secrets and general cleanup. Protect both root archives `ukho-copilot-toolkit-1.0.0.vsix` and `ukho.copilot-toolkit-1.0.0.vsix`. No new Wiki or documentation root is created.
- **Approach:** establish the short shared contract, reconcile roles and methods, replace obsolete assertions with meaningful invariants, then reconcile documentation and run integrated checks. Keep current named roles, existing Node/CommonJS tooling and independent verifier result groups. Reject both another narrow repair exception and unrestricted autoapproval.
- **Bootstrap boundary:** this Plan is authored under the currently loaded schema and authority rules. Its hierarchy maps known owners; it does not purport to predict every debugging action. The replacement contract below is intended source content, not permission to override loaded instructions. Implement must use currently available, permitted routes while authoring it. If loaded restrictions prevent a necessary repair, ask promptly about that precise conflict instead of silently ending or claiming that newly written prose already governs the session.

### Chosen replacement contract

These decisions specify the intended future policy; they do not activate it in this session.

1. **Outcome authority and recovery.** An approved Plan defines behavior, acceptance, change boundary and material constraints. Implement owns ordinary investigation, related-file/test selection and local implementation details within that boundary. A projected file list is guidance, not an automatic exhaustive whitelist. Diagnose failures, correct an implementation or invocation, rerun relevant checks and preserve original acceptance. Restore attributable accidental changes using the actual diff/preimage without overwriting user work. No universal retry quota, unchanged infinite replay, routine commit/backup ritual or whole-workspace hashing. Ask promptly when there is no supported useful next action; continue unaffected work.
2. **Material boundary.** New requirements, materially changed public behavior, consequential dependencies, altered security/compatibility commitments or additional external effects require an engineer decision and Plan-owned scope amendment/new Plan as appropriate. Actual platform denial is not a fallback opportunity. Reconcile uncertain destructive/external completion before repetition. Ordinary failing local checks are not inherently uncertain deployments. Failure keeps dependent acceptance unmet, not diagnosis prohibited.
3. **Role capability.** Keep Implement's existing `read, search, edit, agent, runInTerminal` declaration and remove the cleanup-only execution restriction. Add `runInTerminal` to Implementation Worker's existing `read, search, edit`; it gets no agent tool or lifecycle ownership. Keep Runner `read, search, runInTerminal`, no edit/delegation, as an optional execution specialist. Keep Research/Plan/Review tools unchanged and their source edits prohibited. Keep other workers/reviewers read-only. Use specialist and Stage Assurance delegation when useful, not mandatorily per unit. Retain explicit coordinator allow-lists. A missing specialist permits only an actually available same-scope route, otherwise a specific capability question; never denial evasion.
4. **Review correction and entry.** Keep all handoffs manual (`send: false`). Review classifies each finding by severity, actionable/unclear, and original-criteria correction/material change. For supported in-boundary corrections, the engineer resumes Implement with the original approved Plan and linked Review context, without a new issue Plan or duplicate outcome approval. The original Plan supplies authority; findings supply evidence. Produce fresh implementation evidence and fresh independent Review. New material scope takes the Plan route. Mixed findings allow independently supported corrections but prevent acceptance until unresolved findings are settled. Review does not edit source or delegate implementation. Change `remediate-review` to Implement and explicitly document its changed semantics; it must refuse material expansion and point that work to Plan.
5. **Prospective records.** Retain existing numbered folders/suffixes, suitable documentation-root selection and the twelve instruction patterns. Keep real contained physical records, inspected predecessor kind/content, direct same-folder links and approval context. One compact identity/lineage section is enough; remove duplicate canonical path fields, mandatory fingerprints, double inventories and status-write rituals. Inspect the intended location/current content, select a non-overwriting number, save and inspect the result; on a collision re-read and select an absent next number in the same verified topic, not overwrite or infer a different subject. Preserve approved substantive Plans and finalized reports. Record corrections/progress in new implementation and Review reports; do not rewrite earlier evidence. Status mirrors are optional bookkeeping, not approval or acceptance. A verified clean Review records acceptance; a failed status mirror cannot erase technical evidence, and a failed save must never be reported as persisted. Genuine identity/containment ambiguity still needs resolution; no new mandatory probe catalogue replaces the removed rituals.
6. **Questions and schemas.** Clear Research requests proceed without a compulsory confirmation pause. Ask contextual material questions promptly with a recommendation; lettered choices are optional when genuinely helpful. Allow genuine open questions and factual investigation in all stages. Plans retain one outcome/work register and useful execution guidance, but not compulsory prediction of every file, branch and debugging action. Templates lead with the useful stage result and end with concise traceability and limitations. Partial implementation remains a checkpoint, not successful delivery.
7. **CI and release separation.** Convert the existing automatic workflow to checks-only validation with independent contract, scenario and packaging-guide checks. Keep Node 22.14.0 and current checkout/setup versions; remove the npm dependency cache/install prerequisite for dependency-free checks. Retain the packaging job only as visibly disabled (`if: false`) under the hold, with no new dispatch/approval mechanism. Do not run the workflow remotely in this pass. Existing package commands, version and contribution lists remain unchanged; add only the scenario script entry.

No engineer-owned scope choice remains unresolved for this authored/static pass. The manual correction route, minimal record schema and checks-only CI are explicit design selections above, subject to approval through the receiving Implement invocation. Runtime capability/attachment is unestablished, not assumed; it affects later behavioral proof, not the ability to author and statically test this replacement.
