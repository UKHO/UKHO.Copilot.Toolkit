# Research brief: Restore trackable plan work hierarchy

## Answer and scope

- **Question and answer:** What is needed to restore the earlier Work Item → Task → Step tracking in the active implementation-plan template? Restore a single traceable Work Item register plus corresponding numbered, checkable Task and Step detail as the normal prospective Plan schema. Align the owning planning guidance and add focused static regression coverage where useful. Do not roll back current lifecycle, safety, authority or identity rules.
- **Success and boundaries:** A new Plan can show what is intended and what has been done at each of the three levels, connect each item to evidence/acceptance, and retain outcome, boundaries, validation, assumptions, risks, lineage and manual approval. This is research only: no customization, source, historic Plan, test or packaging change is approved or performed. Whether future Plans must always include all three levels for even trivial changes is an implementation-policy nuance; the engineer's stated preference supports a normal default, not gratuitous empty levels.
- **Provenance:** Initiating engineer request in this VS Code chat on 2026-10-08, asking to revert the current plan template to the earlier work-item/task/step approach, with `docs/planning` as example evidence. No Research phase predecessor or invented local locator for the chat.

- **Patterns and options:** Prefer a prospective revision to `.github/skills/architecture-planning/implementation-plan-template.md`: one authoritative Work Item table with numbered item/outcome, evidence/criterion and optional execution checkbox; matching `### Work Item N` detail with `Task N.M` and `Step N.M.K` checkboxes, relevant target/actions, dependencies, item acceptance and checks. Keep Work Item rows and detail synchronized, no duplicate rival work register. Align `.github/skills/architecture-planning/SKILL.md` to direct Plan to use the hierarchy while preserving the agent's ownership. The alternative of only adding an example under an optional Task/Step sentence is smaller but does not reliably meet the engineer's tracking goal; wholesale copying an old Plan risks reinstating obsolete procedural restrictions.
- **Assumptions and risks:** Interpret “original” as restoring the trackable structure, not replacing every newer template clause verbatim. Too many compulsory micro-steps can encourage invented actions, stale checkmarks and overconstrained implementation; use meaningful steps and a proportionate one-item hierarchy for small work. Checkbox completion records execution progress only, not test pass, stage approval or Review acceptance. Historical numbered Plans remain unchanged.

Preserve the current outcome/boundary/validation/lineage fields and existing phase authority. Do not migrate earlier records.
