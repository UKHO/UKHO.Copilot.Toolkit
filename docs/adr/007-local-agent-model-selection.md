## Context and problem

The Toolkit contributes 18 agents with distinct reasoning demands and authority boundaries but no role-specific model configuration. Users can select the most powerful model for every role without useful defaults. The engineer prioritizes output quality and wants the Research allocation turned into automatic model selection, while accepting truthful effort limitations where Local has no supported per-role control. New agents and maintenance must remain consistent with that approach.

Research recommended nine Sol/high, five Terra/high, three Terra/xhigh, and one Luna/high. That allocation reflects role contracts, engineer-supplied model information and lower-model/higher-effort experience, and engineering judgment. It is not benchmark-proven equivalence or measured cost optimization. The engineer chose mandatory automatic models rather than guidance-only completion and selected Local for this delivery after considering dual-harness feasibility. Copilot compatibility remains a separate follow-on.

Current documentation explicitly describes Local child model preferences but is narrower about root `model` use. Plan's read-only feasibility investigation inspected Microsoft's `1.130.0` implementation: parsed agent model metadata reaches the active root mode, and the chat input observes it and attempts `switchModelByQualifiedName`. The current source counterpart retains that mechanism with guards. This supports a native root-selection design; it does not certify installed routing, exact model references, entitlement, or all supported builds. Importantly, an unmatched root preference can leave the prior model selected: native preference is not fail-closed enforcement.

The extension's existing static contribution/resource mechanism can distribute one internal Skill and linked profile. A canonical table only under `docs/` would not serve installed consumers because that tree is outside the extension payload. Replicating independent tables in agents, templates, and user documentation would invite drift.

## Decision and conditions

### D1 — Automatic assigned models with supported-only effort controls

- **Choice and rationale:** Adopt the complete initial allocation below as the default profile and require automatic selection of the assigned model for every current role on its supported Local paths. Merely documenting a recommendation, manually choosing every role's model, or inheriting a different parent model does not satisfy delivery. Retain the target effort for every role and configure it only through a supported control; unsupported effort may remain explicitly labelled guidance. No invented context-size, token-limit, temperature, or effort field is added.
- **Realistic alternatives and reasoning:** Guidance-only preserves current user choice and avoids routing dependencies but does not meet the engineer-selected result. Mandatory automatic model-plus-effort for every child would demand controls not established in Local. Auto or fallback lists prioritize runtime selection/availability rather than this exact role allocation. The selected model/effort split meets the requested automatic-model outcome without pretending that child effort is enforced.
- **Actual selection or pending state:** The engineer explicitly selected automatic models with unsupported effort permitted as guidance. The allocation is retained from the inspected Research recommendation as the Plan's concrete baseline. Sign-off of this complete ADR snapshot remains pending the qualifying explicit `/implement` invocation; it is not inferred from the clarification answers.
- **Conditions and affected Work Items:** Plan Work Items 1–4 maintain profile consistency; Work Item 2 must demonstrate automatic selection for every role and applicable Local entry/delegation path, with floor/current compatibility evidence. Unsupported effort alone is not a failure; unavailable mandatory model observations keep delivery acceptance unmet. A factual incompatibility constrains dependent effects and takes engineer-directed resolution, not silent guidance-only fallback or changed role assignments.

### D2 — Native Local preferences, explicit exceptions, and truthful failure behavior

- **Choice and rationale:** Target Local only for this pass, retaining `engines.vscode: ^1.130.0`, current roles/tools/delegate lists, and manual phase transitions. Use verified single-model agent `model` preferences as the primary native root/child configuration. Only when bounded compatibility evidence demonstrates a need on an existing prompt/handoff route may a supported same-profile native model projection be added there; keep invocation manual and `send: false`. All projections must agree with the canonical profile. No new runtime router, hook, proxy, BYOK layer, or required user-setting change is introduced.
- **Realistic alternatives and reasoning:** Dual-harness delivery needs separate entry, delegation, tools, selection, and authority-parity work; adding headers does not establish it. Copilot-first changes more than model targeting. Pinning every prompt/handoff upfront creates extra shadowing/drift surfaces without demonstrated need. A custom enforcement layer adds infrastructure and permissions beyond this objective. Native role preferences with bounded existing-route projections are the least-complex selected approach supported by current source evidence.
- **Actual selection or pending state:** The engineer selected Local-only delivery and a separate Copilot follow-on. The detailed native-preference and supported-only override/failure contract is the Plan-selected proposal in this record; exact-record sign-off is not yet claimed. Copilot is not permanently excluded and is not certified by this change.
- **Conditions and affected Work Items:** Work Items 1, 2, and 4 implement/explain this contract; Work Item 3 protects it in authoring/maintenance. Verify exact references, root/child selection, applicable floor/current behavior, and relevant Local child cost-tier restrictions. Explicit engineer overrides may be documented only through an evidenced supported route; unsupported override is disclosed without removing the automatic default. An overridden run is an exception, not evidence that the default profile selected correctly. Do not promise universal picker precedence, silently downgrade, add Auto/Astra fallback, bypass denial, or claim that native metadata blocks wrong-model execution. Detect/report unmatched or unverified effective selection and do not call it profile-compliant. If native Local behavior cannot meet the required default, hold dependent effects/acceptance for engineer direction; do not silently add a harness, raise the engine floor, or build an enforcement service.

Actual routing, effort observation, and compatibility checks require separately bounded activation/model-trial authorization and suitable environments. This ADR, its sign-off, the Plan, and the clarification answers do not provide that separate authorization. Until required observations pass, static implementation can be reported as a checkpoint but not completed delivery. These are delivery-validation dependencies, not an unresolved architectural alternative or a reason to require runtime success before this decision can be signed off.

### D3 — One packaged profile owner and deliberate future-agent classification

- **Choice and rationale:** Add an internal `.github/skills/agent-model-selection/SKILL.md` with one linked `references/role-profiles.md` resource, using existing contribution and payload conventions. The Skill owns the portable capability/consequence selection method; its reference owns the active allocation. Native configuration is an explicitly checked projection, not configuration inheritance from a Markdown link. Existing agents, agent/prompt creation Skills/templates, maintenance guidance, tests, and consumer documentation reuse that owner.
- **Realistic alternatives and reasoning:** A docs-only source is unavailable in the installed payload. Keeping the profile only in the agent-creation Skill mixes creation with ongoing operation. Independent per-agent/template/document tables invite incompatible updates. A runtime generator/router adds machinery without a demonstrated need. The focused resource-backed Skill follows existing packaging and authoring patterns without a new role or tool grant.
- **Actual selection or pending state:** This is the Plan coordinator's selected design, proposed for exact-snapshot sign-off with D1/D2. No separate engineer agreement or runtime loading success is claimed. Grouping is meaningful because these three choices jointly define one role-profile contract and delivery objective; each remains independently identifiable here.
- **Conditions and affected Work Items:** Work Item 1 creates/registers the shared owner; Work Item 2 adopts it; Work Item 3 updates authoring/maintenance; Work Item 4 completes focused checks/docs. A future suite agent must have a justified capability/consequence classification, one profile entry, and supported automatic Local model configuration before being called profile-compliant. Do not hardcode a permanent 18-agent ceiling, silently default unknown roles, or weaken existing explicit role/tool safeguards. Retain least privilege, exact delegate restrictions, advisory assurance, independent Review, and manual phase authority. Profile escalation changes capability/cost, never permission or scope.

## Consequences

- **Benefits:** Expected consistent role defaults, clear supported-setting limits, and a reusable authoring route for future roles. The concrete profile is retained rather than deferred to a benchmark.
- **Risks and technical debt:** Model availability and names change. Native unmatched preferences may retain another model; prose and static tests cannot guarantee execution prevention. Child effort, override, all invocation paths, and range-wide compatibility remain evidence-dependent. No measured quality equivalence, savings, or all-user entitlement is established.
- **Operational impact:** Static customization/resources/checks/documentation change. No new service, tool grant, account setting, dependency, packaging operation, activation, or automatic phase transition is introduced. Copilot support remains separate.
- **Reversibility and recovery constraints:** Restore attributable profile/metadata/doc changes from inspected preimages while preserving user work; no Git cleanup/history rewrite is implied. If an accepted design changes materially, use the actual Plan/ADR amendment route; do not rewrite accepted rationale.
- **Dependencies:** Exact supported editor references; selected Local native mechanisms; actual permission and separate runtime authorization; floor/current environments and observations for completion. Plan Work Item 2 owns the bounded factual resolution route and escalation. Independent approved profile/authoring/static-test/doc work may continue while dependent checks are unavailable.

## Standards and practice alignment

Use the Toolkit's inspected resource-backed Skill pattern, explicit least-privilege agent boundaries, manual RPIR transitions, static manifest discovery, and documented/source-backed native VS Code controls. Preserve the actual consumer engine range and ignored/local-only lifecycle-record policy. This is not a security certification, organizational approval matrix, assurance of runtime instruction adherence, or assertion that selected models have particular pricing/entitlement.
