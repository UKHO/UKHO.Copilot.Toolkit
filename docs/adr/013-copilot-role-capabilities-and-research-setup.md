## Context and problem

The current roles express capability categories, permitted workers and manual handoffs using Local-oriented metadata. Research's inspected released Copilot conversion path transports nonempty tool lists, agent bodies and named skills, but does not project the Local per-parent `agents` filter. Empty/missing lists become an all-tools representation on that path. Transport is not proof of strict tool isolation or disabled nested delegation.

The engineer accepts practical native controls rather than requiring a new enforcement host. Preserve the role obligations without misrepresenting prose as platform enforcement. Required shared guidance must reach each role; a Markdown link or assumed parent inheritance is not loading evidence.

Research also previously failed to attempt necessary folder creation in a supplied example. An existing dedicated directory operation is supported by inspected source, but actual role exposure and permission remain runtime facts. Broadening Research/Runner terminal or file-authority boundaries is not the selected repair.

These decisions share the native role-capability projection and its assurance limits. Individual D sections preserve their separate conditions and future change boundaries.

## Decision and conditions

### D1 - Minimal native capabilities plus explicit behavioral delegation boundaries

- **Choice and rationale:** Give each existing role a justified nonempty list of supported tool aliases or verified qualified client references, preserving its current capability categories. Put each coordinator's existing exact permitted-worker list in its loaded body. Workers explicitly decline nested delegation and effects beyond their assigned authority. Coordinators send bounded briefs, resolve discovered native role identity and reconcile returned evidence/effects.
- **Realistic alternatives and reasoning:** Retaining only Local `agents` metadata does not establish a Copilot filter. Empty tools can broaden exposure. Hooks/brokers add executable machinery without demonstrating complete fail-closed native boundaries; an owned host changes the product. Coordinator-only substitution drops the specialist-assisted outcome. Native projections plus explicit behavioral rules are the selected practical mechanism.
- **Actual selection or pending state:** The engineer selected the practical assurance level and retained roles. This exact configuration/behavioral contract is the Plan's Proposed mechanism, not a runtime guarantee.
- **Conditions and affected Work Items:** Work Items 1-4. Preserve Research/Plan/Review record-specific write limits and no terminal grants; observational workers remain read-only. Implement/Implementation Worker retain approved scoped edit/check capability. Runner remains read/search/terminal-only, without source/record authorship or delegation, and alone executes authorized Git metadata effects. Do not hardcode generated IDs or silently substitute a generic worker. Missing/ambiguous roles stop dependent delegation; unexpected tool exposure is disclosed and unused, not authorization. Do not claim a per-parent native filter, complete default-tool exclusion or adversarial sandbox.

### D2 - Explicit role-appropriate named skills carry shared procedures

- **Choice and rationale:** Use supported named existing skill preloads for essential role-specific procedures and retain concise role ownership/exclusions in agent bodies. Validate that named skills resolve against the contributed/discovered inventory and observe loading when authorized.
- **Realistic alternatives and reasoning:** Links alone do not prove loading. Children do not automatically inherit parent skills. Copying all procedures into every agent creates competing owners; a new shared routing framework adds unnecessary abstraction. Explicit appropriate preloads reuse the existing resource-backed capabilities.
- **Actual selection or pending state:** A complete Plan proposal; no runtime loading success or new procedural framework is claimed.
- **Conditions and affected Work Items:** Work Items 1-4. Keep worker-specific delegated-analyst boundaries and avoid preload-driven authority expansion. Update authoring/templates/checks with the projections. Missing required skills are defects/dependent evidence gaps, not permission to silently ignore their contracts.

### D3 - Research uses the existing dedicated directory operation for selected setup effects

- **Choice and rationale:** Research inspects/reuses or conditionally creates its selected documentation root, direct `copilot` parent and numbered topic one effect at a time through the existing dedicated directory operation. Separately guard the brief's save and full readback. Recursive tool capability is not permission to create unselected ancestors.
- **Realistic alternatives and reasoning:** Manual setup can recover but does not deliver automation. Implicit parent creation hides the missing directory attempt. A Research shell grant, Runner directory authorship or new integration broadens authority rather than fixing the selected use of an existing operation.
- **Actual selection or pending state:** Automatic guarded setup is a carried engineer requirement; use of the existing dedicated operation is the Plan's Proposed implementation.
- **Conditions and affected Work Items:** Work Items 1, 3 and 4. Verify each identity, actual containment, absence/case/file collision, effective permission, created/saved result and readback. Reuse safe directories without setup writes. Missing capability/denial stops that effect and is reported; never evade it via terminal, Runner, implicit parents or a different location. Manual recovery is reported as recovery. Existing-folder file persistence does not pass an absent-root test.

## Consequences

- **Expected benefits:** Supported native configuration with preserved role/specialist administration and explicit attempted Research setup.
- **Risks:** Behavioral controls can be violated; unexpected defaults may remain exposed. Static tests protect authored obligations, not runtime isolation, universal skill inheritance or actual permission.
- **Operational impact:** All role definitions, authoring guidance, owner-local tests and documentation change together. Keep exact existing worker routes and no new capability categories.
- **Recovery:** Correct supported in-scope projection/instruction mistakes and recheck under Implement authority. A required new grant, host, security boundary or worker route needs engineer-directed Plan resolution; actual denial is never a workaround invitation.
- **Dependencies:** Released native transport/directory mechanisms identified in Research, role discovery, required skill availability and separately authorized representative observations. No additional essential enforcement mechanism is promised or deferred to Implement.

## Standards and practice alignment

Uses the existing least-privilege role contracts, named resource-backed skills, lifecycle effect guards and numbered Markdown ADR convention. This is not a security certification or platform restriction claim. A capability declaration never grants an effect outside the role's actual authority.
