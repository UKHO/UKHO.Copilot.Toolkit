## Context and problem

The Toolkit's generic Plan agent and entry command are difficult to distinguish from VS Code's built-in planning workflow. Its converted phase entry Skills explicitly do not select a receiving agent, and the current lifecycle excludes Skill loading from the approval event.

Prompt files could configure an agent in the older Local harness. The Copilot harness uses Skills, whose documented metadata has no equivalent active-agent selector. Internal VS Code commands and deep links provide possible switching paths but are undocumented, can leave the current agent selected after lookup failure, and were not selected for delivery.

The engineer wants manual phase entry to mean sign-off of the previous phase, with no extra routine approval round, and selected the supported two-action route: choose the receiving custom agent, then invoke its Skill. A new Research entry is needed; it has no preceding phase to approve. Bare entry must be useful with established context, and appended text must be retained without depending on prompt placeholder expansion.

The architectural change is the consent and entry contract, not the number of roles, tools, model allocation, host, packaging format or support baseline. Naming remains a routine delivery choice in the associated Plan. The following decisions share the same authority, lifecycle safeguards and rollout, but each is individually identifiable.

## Decision and conditions

### D1 - Deliberate manual Skill invocation is an additional previous-phase sign-off route

- **Choice and rationale:** Retain explicit receiving-agent selection. Once the correct coordinator is selected, an engineer-deliberately sent phase-start Skill invocation can be the receiving-phase request and sign-off event for its identified predecessor, under policy already effective before invocation. Retain deliberate natural-language receiving-agent requests as a supported alternative; the engineer did not request their removal. Do not ask a second routine sign-off question.
- **Exact subject and input:** Research entry starts discovery without predecessor sign-off. Plan-from-Research signs off the inspected Research snapshot for planning. Implement approves only the inspected Plan's bounded outcome. Review signs off the implementation report for independent review admission, not completed delivery or clean acceptance. Bare invocation uses an already explicit, unambiguous objective/predecessor in context; appended information can identify or qualify it. The receiver independently inspects the physical record, kind, substantive version, containment, freshness and direct lineage and freezes the approval subject. Missing, inaccessible, ambiguous, changed or conflicting input requires contextual clarification before dependent effects, not newest-file selection or invented approval. Invoking Research does not acknowledge the later Research readback.
- **Correction and material scope:** Manual Implement or remediation entry resumes supported original-criteria correction under the original approved Plan and inspected Review context; it does not accept the findings as a clean Review or authorize material expansion. A material Review-origin Plan requires the engineer's chosen material scope and inspection of Review, reviewed report, prior Plan and original Research. That invocation authorizes planning, not the resulting Plan's implementation.
- **Provenance and receiver:** Automatic Skill loading, quoted commands, picker selection, worker/tool output, automatic continuation and unsent suggestions are not deliberate engineer invocation. A Skill name does not establish the actual executing role. Wrong or unknown receiver holds mismatched phase-owned effects and offers manual selection with the physical input; no impersonation, automatic dispatch or subagent substitute. Metadata supports discoverability and manual use but does not prove provenance or platform enforcement.
- **Alternatives and reasoning:** Existing plain requests alone avoid another entry surface but do not provide the selected Skill interface. Making Skills mandatory would remove supported behavior without engineer direction. Prompt restoration uses the retiring Local harness; a router or internal-command wrapper adds unsupported behavior and wrong-agent risks. A second routine approval confirmation repeats the action the engineer wanted to avoid.
- **Actual selection and conditions:** Manual invocation as previous-phase sign-off and dropdown-first routing are engineer selections. The detailed phase meanings, retained plain-request route and guards above are this complete Proposed design. Preserve actual authority, physical lineage, independent Review, effect-specific permissions and effective-policy bootstrap; edits do not self-upgrade a loaded session or make earlier invocations retroactive.
- **Affected work:** Associated Plan Work Item 2.

### D3 - Retain distinctive phase entry Skills and add Research entry

- **Choice and rationale:** Keep useful phase-start Skills, give them distinctive RPIR identities and add the missing Research entry. Entry Skills are thin manual adapters to the owning phase methods and lifecycle contract, not new coordinators or duplicated procedural manuals. Declare explicit user invocation and disable automatic model invocation. Do not add unsupported Skill agent selectors or fork main-phase ownership.
- **Alternatives and reasoning:** Retiring all entry Skills follows ADR 012 D3 but conflicts with the selected discoverable Skill interface. Retaining generic names leaves the reported naming clash. Rebuilding Local prompts, plugin routing or an extension dispatcher adds support or architectural obligations outside the selected mechanism.
- **Actual selection and conditions:** The engineer requested a Research entry, selected Skill-based startup after manual agent selection and selected the RPIR naming bundle in the associated Plan. Retain safe input, consent, progress, checkpoint and correction functions in canonical owners. Remove obsolete adapter-retirement instructions from active guidance, not accepted ADR history. No installed discovery, live compliance, role continuity or runtime permission is asserted by static changes.
- **Affected work:** Associated Plan Work Items 1 and 2.

## Consequences and practice alignment

- The workflow has a discoverable phase entry with one deliberate consent event after the user selects the receiver. It does not offer one-action automatic agent switching.
- Existing plain requests, 18-role topology, tool boundaries, profile allocation, Research discovery, exact-record metadata limits, original-criteria correction and independent Review remain intact.
- Naming and metadata are mechanically testable; whether the assistant follows the entry procedure requires reasoned authored assessment and later separately authorized use. No English-policy recognizer or automated semantic judge is introduced.
- Bare entry requires trustworthy contextual identity; it is not a promise that an empty conversation identifies a predecessor. Missing facts cause clarification, not a success-shaped fallback.
- ADR 012 D1's blanket exclusion of Skill invocation and D3's retirement direction are prospectively replaced for this selected entry interface. Its actual-role, physical-input and manual-transition safeguards survive. D2's qualifying request is extended only as specified here. No reciprocal status or substantive edit to ADR 012 is authorized.
- Preserve the existing numbered Markdown ADR convention. Additional governance is applied only if genuinely evidenced; no universal consumer convention or approval body is invented.
